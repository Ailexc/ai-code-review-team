## 三、P0：全代码库上下文（Context Engine）

### 3.1 目标
让每个 Agent 在审查时能**理解整个代码库**，而不只是被审查的单个文件。这是竞品（尤其 CodeRabbit 的 Codegraph、Qodo 的 Context Engine）的核心能力。

### 3.2 技术选型

#### 方案 A：AST + 符号表索引（推荐，确定性）
```
代码库 → AST 解析 → 符号表（函数/类/变量/导入）
              → 调用关系图（谁调用谁）
              → 依赖关系图（文件间 import）
              → 存储为结构化索引
```
- **工具**：Python `ast`（已有基础）+ `tree-sitter`（多语言）
- **优点**：确定性、零误报、可解释、无需外部服务
- **缺点**：只理解结构，不理解语义

#### 方案 B：向量化语义检索（LLM 增强）
```
代码库 → 分块 → Embedding → 向量数据库
审查时 → 语义查询 → 检索相关代码块 → 注入上下文
```
- **工具**：`sentence-transformers` / `chromadb` / `faiss`
- **优点**：理解语义，能检索"功能相似"的代码
- **缺点**：需要 Embedding 模型、有误报、成本高

#### 推荐：A + B 混合
```
第一层：AST 符号表（确定性，建立结构骨架）
第二层：向量检索（语义，补充结构无法覆盖的）
第三层：LLM 上下文组装（把检索结果组织成 prompt）
```

### 3.3 架构设计

```
┌─────────────────────────────────────────────┐
│              Context Engine                 │
│                                             │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  │
│  │ AST 索引  │  │ 向量索引  │  │ 调用图   │  │
│  │ (符号表)  │  │(embedding)│  │(关系)    │  │
│  └────┬─────┘  └────┬─────┘  └────┬─────┘  │
│       │             │             │        │
│       └─────────────┼─────────────┘        │
│                     ▼                      │
│  ┌─────────────────────────────────────┐   │
│  │        Context Assembler            │   │
│  │  把相关代码块组织成审查上下文        │   │
│  └──────────────────┬──────────────────┘   │
└─────────────────────┼─────────────────────┘
                      ▼
              ┌──────────────┐
              │  各 Agent     │
              │  (注入上下文)  │
              └──────────────┘
```

### 3.4 实施步骤

| 步骤 | 内容 | 交付物 |
|------|------|--------|
| 1 | 代码索引服务 `services/code_index.py` | AST 符号表 + 调用图 |
| 2 | 向量化检索 `services/vector_store.py` | Embedding + 语义检索 |
| 3 | 上下文组装 `services/context_engine.py` | 把索引结果组织成 prompt |
| 4 | Agent 接入 | 各 Agent 审查时注入相关上下文 |
| 5 | 前端展示 | 审查详情显示"引用的上下文" |

### 3.5 依赖
```
tree-sitter          # 多语言 AST 解析
tree-sitter-python   # Python 语法
sentence-transformers # Embedding 模型（可选）
chromadb             # 向量数据库（可选）
```

## 四、P1：PR 历史学习（Learning）

### 4.1 目标
让系统从**历史审查记录**中学习团队规范，自动适应团队偏好。对标 Qodo 的 Rule Miner、CodeRabbit 的持续学习。

### 4.2 技术选型

#### 方案 A：规则挖掘（确定性）
```
历史审查记录 → 分析被标记/被忽略的 finding 模式
             → 提取高频规则 → 生成可配置规则
```
- **工具**：现有 Finding 数据 + 统计聚类
- **优点**：确定性、可解释、可配置
- **缺点**：需要足够历史数据

#### 方案 B：反馈闭环（LLM 增强）
```
用户对 finding 的操作（确认/忽略/修复）→ 记录
             → LLM 学习偏好 → 调整后续审查权重
```
- **优点**：自适应、个性化
- **缺点**：需要用户交互数据

#### 推荐：A + B
```
第一层：从历史 finding 统计挖掘高频规则（确定性）
第二层：从用户操作学习偏好（LLM 增强）
```

### 4.3 架构设计

```
┌─────────────────────────────────────────────┐
│            Learning Engine                  │
│                                             │
│  ┌──────────────┐  ┌──────────────────┐    │
│  │ 历史 Finding  │  │ 用户操作记录      │    │
│  │ 统计挖掘      │  │ (确认/忽略/修复)  │    │
│  └──────┬───────┘  └────────┬─────────┘    │
│         │                   │              │
│         ▼                   ▼              │
│  ┌─────────────────────────────────────┐   │
│  │        Rule Store（规则库）          │   │
│  │  高频规则 + 团队偏好 + 权重          │   │
│  └──────────────────┬──────────────────┘   │
└─────────────────────┼─────────────────────┘
                      ▼
              ┌──────────────┐
              │  审查时应用   │
              │  (调整权重)   │
              └──────────────┘
```

### 4.4 实施步骤

| 步骤 | 内容 | 交付物 |
|------|------|--------|
| 1 | 规则模型 `models/review_rule.py` | 规则存储 |
| 2 | 规则挖掘 `services/rule_miner.py` | 从历史 finding 提取规则 |
| 3 | 反馈记录 | 记录用户对 finding 的操作 |
| 4 | 权重调整 | 审查时应用学习到的偏好 |
| 5 | 前端规则管理 | 规则列表 + 启停 |

## 五、P2：语义 diff 理解（Semantic Diff）

### 5.1 目标
让系统理解**变更的意图**，而不只是行级增删。对标 CodeRabbit 的 Change Stack、Qodo 的语义 diff。

### 5.2 技术选型

#### 方案 A：AST 级 diff（确定性）
```
旧文件 AST vs 新文件 AST → 结构化 diff
  - 函数/类级别的变更（而非行级）
  - 识别"重构" vs "新增" vs "删除"
  - 识别跨文件影响（调用方变化）
```
- **工具**：`tree-sitter` + 自定义 AST diff 算法
- **优点**：确定性、精确、可解释
- **缺点**：实现复杂度高

#### 方案 B：LLM 变更意图分析（增强）
```
AST diff 结果 → LLM 分析变更意图
  - 这个变更想做什么？
  - 影响哪些调用方？
  - 是否有遗漏的配套修改？
```
- **优点**：理解意图、发现逻辑问题
- **缺点**：依赖 LLM、成本高

#### 推荐：A + B
```
第一层：AST diff（确定性，识别结构化变更）
第二层：LLM 意图分析（理解变更目的 + 跨文件影响）
```

### 5.3 架构设计

```
┌─────────────────────────────────────────────┐
│           Semantic Diff Engine              │
│                                             │
│  ┌──────────────┐  ┌──────────────────┐    │
│  │ AST Diff     │  │ 调用图影响分析    │    │
│  │ (结构化变更)  │  │ (跨文件影响)      │    │
│  └──────┬───────┘  └────────┬─────────┘    │
│         │                   │              │
│         ▼                   ▼              │
│  ┌─────────────────────────────────────┐   │
│  │      LLM 意图分析                    │   │
│  │  变更目的 + 影响范围 + 遗漏检查      │   │
│  └──────────────────┬──────────────────┘   │
└─────────────────────┼─────────────────────┘
                      ▼
              ┌──────────────┐
              │  审查 Agent   │
              │  (理解意图)   │
              └──────────────┘
```

### 5.4 实施步骤

| 步骤 | 内容 | 交付物 |
|------|------|--------|
| 1 | AST diff `services/ast_diff.py` | 结构化变更识别 |
| 2 | 调用图影响分析 | 变更影响哪些调用方 |
| 3 | LLM 意图分析 | 变更目的 + 遗漏检查 |
| 4 | Agent 接入 | 审查时注入变更意图 |
| 5 | 前端展示 | 审查详情显示"变更意图" |

## 七、技术选型汇总

| 模块 | 技术 | 理由 |
|------|------|------|
| AST 解析 | `tree-sitter` + `tree-sitter-python` | 多语言、增量解析、鲁棒 |
| 符号表/调用图 | 自定义（基于 AST） | 确定性、可解释 |
| 向量检索 | `chromadb` + `sentence-transformers` | 轻量、本地、语义检索 |
| 规则存储 | SQLite（现有） | 复用现有数据库 |
| 语义 diff | 自定义 AST diff | 确定性、精确 |
| LLM 意图分析 | 现有 LLM 客户端 | 复用 |
| 可观测性 | 现有 metrics + 扩展 | 复用 |

## 十、风险与注意事项

| 风险 | 应对 |
|------|------|
| 向量检索误报 | AST 确定性索引兜底，向量仅补充 |
| LLM 成本上升 | 上下文组装时限制 token，缓存索引 |
| 实现复杂度 | 分阶段实施，每阶段可独立验证 |
| 多语言支持 | tree-sitter 支持 10+ 语言，逐步扩展 |
