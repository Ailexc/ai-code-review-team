1. 起点：一次系统完整度评估

对系统做了 10 个维度的完整度评估（学习项目视角 9/10，生产工具视角 5.5/10），其中三个维度的扣分项经讨论后立项改进：

维度扣分项处置决策
核心功能多语言"名不副实"；Agent 间无真正协作按项目管理内 3 个应用的语言做真实标准工具支持；加编排模式对比开关
架构设计单进程强绑定；context 体系疑似重叠接口预留不实现；查证后推翻"重叠"结论，实为并发竞态 bug
可观测性WS 子步骤实时粗；Langfuse 未接前端消费已有 step_* 事件；Langfuse 决定不引入（自建档案已够）

方法论收获：评估结论也要接受再核查——"疑似重叠"经代码查证实为「引擎层 + 适配层」的两层设计，真正的问题藏在背后（全局单例竞态）。

3. 任务①：context 引擎并行竞态修复

问题本质：agent_context 是带可变状态的全局单例（_engine / _project_path），6 个 Crew 并行时各自调 build() 互相覆盖——单审查同项目时碰巧无害，多项目并行审查会数据串味。附带问题：full 审查同一项目索引被重复构建 6 次。

修复设计（两个原则）：

  • 构建上移：索引构建从"每个 Agent 自己 build"上移到 Flow 层，每次审查构建一次
  • ContextVar 注入：engine 经上下文变量随审查链路传播（复用 current_review_ctx 先例）， enhancer 变成无状态函数；按 (project_path, file_paths) 做实例缓存，dict 赋值原子性保证并发安全（最坏情况重复构建一次，正确性不受影响）
💡 学习点：全局单例 + 可变状态 + 并发 = 隐性雷区。单进程协程并发下即使"碰巧没事"，也只是时序运气。评审这类代码时先问：这个单例的状态会被几个执行流写？

4. 任务③：编排模式开关（并行 ↔ 派发）

学习动机：用户提出与其只加"交叉洞察"，不如做成可切换的编排模式，直接对比两种范式的差异——这比单纯加功能更有学习价值。

模式机制特点
⚡ 并行（默认）Flow 多 @listen 驱动 6 个独立 Crew → 代码层去重聚合快、省 token、结果稳定
🎯 派发（实验）单个 Crew 容纳全部 Agent，Process.hierarchical 由 Manager LLM 统一调度，Agent 可互相委派token 数倍消耗，输出依赖模型能力

实现要点：

  • Review 模型加 orchestration_mode 列——SQLite 的 create_all 不会给已存在的表加列，在 init_db 里用 PRAGMA table_info 检查后安全 ALTER（幂等）
  • Flow 的 and_() 聚合是静态结构：让 6 个节点都检查模式，派发模式下第一个抢到实例锁的节点执行整体派发 Crew，其余快速返回——不改聚合拓扑就完成模式分发

5. 任务④：多语言"真实支持"补齐

用户的原话定了调性："确确实实是符合标准规范的支持，而不是什么兼容了、降级了、模拟了。"由此确立原则：

📏 原则：确定性层只用各生态的官方事实标准工具（Ruff / ESLint / golangci-lint / pip-audit / npm audit / OSV-Scanner / Semgrep）；没有标准工具等价物的维度（如测试覆盖/性能分析的非 Python 分析），明确标注由 LLM 语义层承担——诚实标注好过假支持。

接入的四个标准工具：

缺口选型理由
TS/JS 规范ESLint 9 + typescript-eslint业界事实标准；全局安装 + 内置推荐规则，目标项目无需本地依赖
Go 规范golangci-lintGo 官方推荐 meta-linter（聚合 errcheck/staticcheck/govet 等）
JS 依赖漏洞npm auditnpm 自带标准，与已有 npm outdated 同构
Go 依赖漏洞OSV-ScannerGoogle 官方多生态漏洞库扫描器，解析 go.mod 无需 Go 工具链

语言路由实现：code_style_agent 按检测到的语言分发到对应工具（Python→Ruff，TS/JS→ESLint，Go→golangci-lint），子步骤统一记为 lint_check 并标注语言与工具名。

端到端验收实录（真实审查时间线）：

Go 项目 code_style：
[lint_check] 🔍 golangci-lint 静态检查（go）：命中 0 条（2.0s）

JS 项目 code_style：
[lint_check] 🔍 ESLint 静态检查（typescript）：命中 0 条（1.3s）
[llm_file_analysis] 🧠 LLM 语义分析 eslint.config.js：发现 1+4 个问题

命中 0 条是真实结果：go-openai 是官方维护的成熟库；JS 项目用自己的 eslint.config.js 跑自然干净。而 LLM 层补充发现了配置文件里的问题——"规则引擎 + LLM 互补"机制正常工作。

6. 深挖：golangci-lint 的静默假支持

这是本轮最有价值的踩坑，完整还原：

层次问题发现方式
flag 层v1.61 的 flag 是 --out-format，写成 --output-format 直接报 unknown flag容器内手动执行看 stderr
运行时依赖层golangci-lint 做类型检查需要调用 go 命令加载包——镜像里删掉 Go 工具链后报 go command required, not foundexit=3 + stderr 日志
目标配置层目标项目的 .golangci.yml 启用了 v1.61 不认识的 linter（gomodguard_v2 等）--no-config + --enable-only 固定核心集规避
⚠️ 最危险的坑：静默失败 = 假支持。Agent 代码对工具异常做了 try/except 返回空列表（本意是优雅降级），但副作用是——工具装了、跑不通、结果为空，时间线上却一切"正常"。如果不去容器里手动跑一遍工具本身，这个 bug 会永远藏下去。

对策：① 保留 Go 工具链进最终镜像（+150MB 换真实能力，用户拍板）；② ENV GOPROXY 同时服务构建期安装与运行时类型检查的模块下载；③ GOPATH/bin（/root/go/bin）必须进 PATH（go install 产物默认装在这，不在 /usr/local/bin）。

第一性原则回顾：验收标准是"真实支持"，那么"工具能被调用"不算完成，"工具能在目标项目上产出正确结果"才算。所有静默 except 都是这条标准的敌人。

7. 国内镜像源实测与固化

起因：镜像构建时 pip/npm/GitHub 下载极慢，用户问"有没有切国内镜像"——由此做了一轮系统性实测。

环节实测结果结论
pip 阿里云✅ 0.47s | npm 淘宝 ✅ 0.44s | apt 阿里云 ✅ 0.24s基础三件套直接固化
GitHub 公共代理❌ ghproxy.cn 假 200 断流（7MB 只下 7KB）；ghproxy.net 14~52KB/s 且中途断流；ghfast.top / gh.llkk.cc / moeyy 全挂公共 ghproxy 全不可靠，放弃
Go 官方中国镜像✅ golang.google.cn 1.5MB/s；goproxy.cn 响应 0.54s正解：Go 工具链 + go install 全程走官方国内镜像

固化的 Dockerfile 要点：

# apt 换阿里云（sed 替换 debian.sources）
# npm 换淘宝：npm config set registry https://registry.npmmirror.com
# pip 阿里云：ENV PIP_INDEX_URL=... （注意：不要配 PIP_NO_CACHE_DIR=1，
#   它会禁用缓存写入，使 --mount=type=cache 形同虚设）
# Go 工具链 + golangci-lint + osv-scanner：
ENV PATH="/usr/local/go/bin:/root/go/bin:${PATH}" GOPROXY="https://goproxy.cn,direct"
RUN curl -sSfL -o /tmp/go.tgz https://golang.google.cn/dl/go1.23.4.linux-amd64.tar.gz \
    && go install github.com/golangci/golangci-lint/cmd/golangci-lint@v1.61.0 \
    && go install github.com/google/osv-scanner/cmd/osv-scanner@v1.9.2

两个层缓存优化：

  • 工具层移到 pip 层之后：Docker 缓存按层失效，改工具版本不再触发 pip 全量重装（本次实测 pip 重装耗时 400s+）
  • semgrep 加版本上限（<2）：换镜像源会导致 pip 解析出不同版本（1.174.0 → 1.173.0），上限约束消除漂移

8. 经验教训

  • 评估结论也要再核查："疑似重叠"查证后是两层设计，真问题是背后的单例竞态——负责任的评估应该敢于修正自己。
  • 静默 except 是假支持的帮凶：优雅降级代码会把"工具跑不通"伪装成"没有问题"。凡是声称"支持 X"，必须有端到端的真实结果验证。
  • 网络问题先横向测速再选型：本轮在 ghproxy 上串行试错耗了半小时，最后一轮横向测速 10 分钟解决。候选方案先并行验证，不要串行试错。
  • Docker 层缓存的失效是连锁的：前置层变更会让后续所有层重建；把易变层放后面、把贵层（pip）放前面保护起来。
  • 用户的原则是最好的选型标准："不搞模拟降级"一句话否决了所有偷懒方案，也催生了"LLM 层诚实标注"这个更清晰的产品表达。
