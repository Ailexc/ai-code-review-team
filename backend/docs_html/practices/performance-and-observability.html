1. 背景与目标

系统基于 CrewAI Flows + Crews 双层架构做代码审查。真实环境暴露两个问题：

  • 性能慢：单 Agent 安全审查耗时 453 秒（7.5 分钟），主要瓶颈在 Semgrep 联网下载规则 + 串行扫描 + CrewAI 收尾 LLM 重新格式化
  • 过程黑盒：审查记录只有最终问题列表，用户看不到"每一步做了什么、耗时多少、跳过了什么"，无法学习整套流程

目标：① 大幅提速且不影响审查能力；② 让每一步执行过程可持久化、可回看、可学习。

2. 性能优化（3 项）

通过日志拆解，453 秒的构成：

阶段耗时优化
Semgrep 6 规则集扫描较大（联网下载 + 串行）规则本地化 + 并行扫描
LLM 文件分析中（已并行 concurrency=3）无需改动
CrewAI 收尾 LLM~86s（大头）result_as_answer 跳过

3. Semgrep 规则本地化

调研结论：Semgrep 的 registry 规则（p/python 等）每次联网拉取、不持久缓存（实测 ~/.semgrep 为空）。且部分规则集（p/sqlalchemy、p/python_audit、p/spring）在免费 Registry 不可用，会 code=7 退出。

方案：git clone 官方 semgrep/semgrep-rules 仓库到本地，用本地目录做 --config，彻底离线。

# 稀疏克隆（只取所需语言），规则包仅 8.6MB
git clone --depth 1 --filter=blob:none --sparse https://github.com/semgrep/semgrep-rules
git sparse-checkout set python javascript typescript java go
# 扫描时用本地目录
semgrep scan --config /app/app/data/semgrep-rules/python --metrics=off ...

收益：完全离线（零网络延迟）、规则更全面（python 337 条 vs registry 151 条）。Dockerfile 构建时自动 clone，生产可复现。

4. 跳过 CrewAI 收尾 LLM

关键认知：工具返回的 findings 已是确定的最终结果（schema 确定），CrewAI 却默认让 Agent 再调一次 LLM 重新格式化——这是重复劳动 + 大输入（17 条 findings 完整 JSON 塞给 LLM，单次 86 秒）。

调研与实测：CrewAI 原生支持 @tool(name, result_as_answer=True)，让工具结果直接作为最终答案，跳过收尾 LLM。

@tool(f"{agent_name}_review_scan", result_as_answer=True)
async def review_scan(path: str = "") -> str:
    findings = await agent.analyze(project_path=target, file_paths=file_paths)
    return json.dumps({"findings": findings}, ensure_ascii=False)  # 必须返回对象

实测验证：async tool + result_as_answer=True 在项目现有 kickoff_async 路径下完全可行（51.6s / 17 findings / 零收尾 LLM）。Agent 的"思考 → 决定调工具"学习价值完整保留，只省掉重复表述。

⚠️ 踩坑：tool 必须返回 {"findings": [...]} 对象，不能返回顶层数组。否则 Task 的 output_pydantic=FindingsOutput 校验失败（Invalid JSON: trailing characters）。

5. 过程可观测性

问题：原 progress_emitter 是内存级事件总线，审查结束即清理，过程不持久化。

方案：新增 review_steps 表，持久化每一步执行记录。

字段说明
phaseouter_flow / inner_crew
node_typeparse_project / run_*_crew / aggregate / generate_report / skip_agent
statuscompleted / skipped / failed
action_text中文描述"这一步做了什么"（学习核心）
input/output_summary输入输出摘要
duration_ms耗时
detailJSON 详情（tokens/异常/跳过原因）

每个节点完成后调用 review_step_recorder.record() 落库；新增 GET /reviews/{id}/steps API；前端详情页新增「执行流程」时间线面板，展示外层 Flow + 内层 Crew 每一步。

6. 踩坑与修复

  • SQLite 写锁（database is locked）：根因是 review_service 创建 review 后 未 commit，事务在审查期间一直持写锁，阻塞 review_steps/llm_usage 独立 session 写入。修复：创建 review 后立即 commit 释放锁。
  • ReviewStep relationship：Review.steps 用 back_populates="review"，但 ReviewStep 未定义反向关系，导致 SQLAlchemy mapper 初始化失败（500）。修复：补 review relationship。
  • asyncio.Lock 跨事件循环：模块级单例 Lock 绑定事件循环，pytest-asyncio 多 loop 下报错。修复：去掉 Lock，靠 WAL + busy_timeout + 短重试兜底。
  • 并行步骤 sequence 重复：5 个 skip_agent 并行同时 SELECT max 导致 sequence 重复。修复：API 排序加 created_at 兜底。

8. 经验教训

  • 先调研实测，再下结论：曾误判"async tool + result_as_answer 有 bug"，实际是测试脚本用了 kickoff()（sync）而非项目的 kickoff_async()。用与生产一致的路径验证，结论才可靠。
  • 不要"为了学习而学习"：CrewAI 的收尾 LLM 是重复劳动，用 result_as_answer 程序级处理，既提速又不影响 Agent 自主调工具的学习价值。
  • SQLite 并发写要尽早提交事务：长事务持锁会阻塞所有独立 session 写入，是"database is locked"的常见根因。
  • 可观测性是学习工具：持久化每一步的"做了什么/耗时/跳过原因"，让整套流程从黑盒变白盒，是学习多 Agent 编排的最佳方式。
