1. 设计理念

多 Agent 编排是本系统的核心架构模式。为什么用 CrewAI Flows + Crews 双层而不是纯 Crew 或手写编排：

  • 外层要确定性，内层要自主性：任务分解/状态管理/结果聚合必须是白盒、可调试、可中断的确定性流程；各专业 Agent 的审查则是自主的（决定如何调用工具、如何分析）
  • 纯 Crew 是黑盒：框架隐式决定任务分配和执行顺序，调试困难，不适合学习
  • Flow 是白盒：每一步都是确定性 Python 代码 + @start/@listen/@router 装饰器，状态可追踪、可断点调试
  • 学习价值：掌握 CrewAI 的两种范式，能讲清"何时用 Flow、何时用 Crew、何时结合"

2. 双层架构总览

┌───────────────────────────────────────────────────────────────┐
│              外层 ReviewFlow（CrewAI Flow）                    │
│  确定性控制 · 状态管理（Pydantic model）· 白盒可调试            │
│                                                               │
│  @start   parse_project()   → 校验路径 / 初始化状态            │
│  @listen  run_*_crew() × 6  → 并行触发 6 个内层 Crew（Flow 机制并行）│
│  @listen  aggregate()       → 去重 / 统计 / 摘要               │
│  @listen  generate_report() → 完成，输出 ReviewState           │
└───────────────┬───────────────────────────────────────────────┘
                │ 并行调度（多个 @listen 节点同时执行）
    ┌───────────┼───────────┬───────────┬───────────┐
    ▼           ▼           ▼           ▼           ▼
┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐
│安全Crew │ │规范Crew │ │依赖Crew │ │覆盖Crew │ │性能Crew │
│ Agent   │ │ Agent   │ │ Agent   │ │ Agent   │ │ Agent   │
│ +Task   │ │ +Task   │ │ +Task   │ │ +Task   │ │ +Task   │
│ +Tools  │ │ +Tools  │ │ +Tools  │ │ +Tools  │ │ +Tools  │
└─────────┘ └─────────┘ └─────────┘ └─────────┘ └─────────┘
                              （GitCrew 同上）
              内层 Crew：Agent 自主决定如何调用工具完成审查

关键点：并行由 Flow 机制本身提供（多个方法 @listen 同一节点时 CrewAI 并行执行），不依赖手写 asyncio.gather。

3. 外层 Flow（确定性编排）

backend/app/flows/review_flow.py — 外层 Flow 用装饰器声明节点与依赖关系，状态用 Pydantic model 管理：

class ReviewState(BaseModel):
    project_path: str = ""
    project_name: str = "Unknown"
    file_paths: list[str] | None = None
    review_type: str = "full"
    review_id: str = ""
    findings_by_agent: dict[str, list[dict]] = Field(default_factory=dict)
    total_findings: int = 0
    summary: str = ""

class ReviewFlow(Flow[ReviewState]):
    @start()
    def parse_project(self) -> None:
        """节点1：校验路径 + 发布进度事件"""
        ...

    # 节点2：每个 Agent 一个 @listen(parse_project) 节点 → CrewAI 并行执行
    @listen(parse_project)
    async def run_security_crew(self) -> None:
        await self._run_crew("security")

    @listen(parse_project)
    async def run_code_style_crew(self) -> None:
        await self._run_crew("code_style")

    # ...（dependency / test_coverage / performance / git_review 同构）

    @listen(run_security_crew, run_code_style_crew,
            run_dependency_crew, run_test_coverage_crew,
            run_performance_crew, run_git_review_crew)
    def aggregate(self) -> None:
        """节点3：全部 Crew 完成后聚合去重 + 统计"""
        ...

    @listen(aggregate)
    def generate_report(self) -> ReviewState:
        """节点4：完成，返回最终状态"""
        return self.state
  • @start：流程入口节点
  • @listen(A)：监听 A 完成后的节点；多个节点监听同一 A 时并行执行
  • @listen(A, B, C)：等待 A/B/C 全部完成后执行（聚合屏障）
  • 状态驱动：self.state 在各节点间传递，可中断/重试/持久化

4. 内层 Crew（Agent 自主协作）

backend/app/flows/crew_factory.py — 每个专业 Agent 构建一个独立 Crew，实现上下文隔离：

from crewai import Agent, Task, Crew, Process
from crewai.tools import tool

# 1. 确定性审查逻辑封装为 CrewAI 工具（Semgrep/Ruff/pip-audit/AST + LLM 分析）
@tool("security_scan")
async def security_scan(project_path: str, file_paths: list[str]) -> str:
    """对项目执行安全扫描，返回结构化 findings JSON"""
    ...

# 2. Agent：角色 / 目标 / 背景 / 工具
security_agent = Agent(
    role="资深代码安全审查专家",
    goal="全面检测项目中的安全漏洞（SQL注入、XSS、硬编码密钥等）",
    backstory="拥有 15 年应用安全经验，精通 OWASP Top 10...",
    tools=[security_scan],
    llm=crew_llm,
    verbose=True,
)

# 3. Task：任务描述 + 期望输出
security_task = Task(
    description="审查项目 {project_path}：调用 security_scan 工具获取扫描结果，"
                "结合你的安全知识补充分析，输出结构化发现列表",
    expected_output="JSON findings 列表：rule_id / severity / message / file_path / line / suggestion",
    agent=security_agent,
)

# 4. Crew：内层自主协作单元
security_crew = Crew(
    agents=[security_agent],
    tasks=[security_task],
    process=Process.sequential,  # 单 Agent 场景用 sequential
    verbose=True,
)
  • Agent：角色 + 目标 + 背景 + 工具，决定如何完成任务
  • Task：具体任务描述 + 期望输出（可用 output_pydantic 强约束）
  • Crew：组织 Agent 与 Task 的执行单元，Process.sequential / hierarchical
  • 上下文隔离：每个 Crew 独立，Agent 之间不互相污染

5. 并行执行机制

CrewAI Flow 的并行由框架机制提供：多个方法 @listen 同一个上游节点时，CrewAI 会并发执行这些方法。6 个内层 Crew 各自在一个 @listen(parse_project) 节点中 kickoff_async()，从而并行审查。

# 内层 Crew 并行：每个 @listen 节点独立运行一个 Crew
@listen(parse_project)
async def run_security_crew(self):
    crew = build_review_crew("security", self.state)
    await crew.kickoff_async(inputs={...})
    self.state.findings_by_agent["security"] = ...

# 聚合屏障：等 6 个 Crew 全部完成后触发
@listen(run_security_crew, run_code_style_crew, ...)
def aggregate(self): ...

对比手写 asyncio.gather：手写方案把并行、容错、状态管理全部自己实现（易出错、难调试、无学习价值）；Flows 方案由框架负责调度，开发者只需声明节点依赖关系，且每一步状态可见。

6. 结果聚合

所有 Crew 完成后，聚合节点统一处理：

  1. 去重：按 (rule_id, file_path, line_start) 去重（不同 Agent 可能报告同一问题）
  2. 统计：按严重度统计（critical/warning/suggestion/nitpick）
  3. 摘要：生成审查摘要文本
  4. 持久化：由服务层（ReviewService）将 findings 写入数据库

7. 完整代码示例

生产主路径（重构后）：ReviewService.run_review() 委托给 ReviewFlow 执行编排：

# 1. 构建 CrewAI LLM（复用项目 LLM 配置）
llm = build_crew_llm(await get_active_llm_config())

# 2. 运行外层 Flow（内部自动并行调度 6 个内层 Crew）
flow = ReviewFlow()
state = await flow.kickoff_async({
    "project_path": project.path,
    "file_paths": file_paths,
    "review_type": review_type,
    "project_name": project.name,
    "review_id": review.id,
})

# 3. 服务层拿到 findings_by_agent 后持久化 / 统计 / 摘要 / 指标
for agent_name, findings in state.findings_by_agent.items():
    for f in findings:
        db.add(Finding(review_id=review.id, agent_name=agent_name, ...))

8. 学习价值与面试话术

🎓 面试话术：
  • Q：你的多 Agent 系统怎么编排？
    A：采用 CrewAI Flows + Crews 双层架构——外层 Flow 用 @start/@listen 装饰器做确定性编排（解析→分派→运行→聚合→报告），状态用 Pydantic 管理；内层每个专业 Agent 是一个独立 Crew（Agent + Task + 工具），自主决定如何审查。并行由 Flow 的多个 @listen 节点提供。
  • Q：为什么不用纯 Crew 或手写 asyncio？
    A：纯 Crew 是黑盒（执行顺序不透明）；手写编排把并行、容错、状态管理全自己实现，没有框架的调试与可观测能力。双层架构外层白盒、内层自主，是 CrewAI 官方推荐范式，也是学习价值最高的组合。
  • Q：上下文怎么隔离？
    A：每个 Agent 一个独立 Crew，各自独立的上下文，结果由外层 Flow 统一聚合，Agent 之间不直接通信。
