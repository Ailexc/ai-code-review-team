2. 项目亮点与价值点

你将学到什么

  • 如何设计一个多 Agent 并行编排系统：asyncio.gather 并发、结果聚合、容错降级
  • 如何实践"确定性工具兜底 + LLM 语义补充"的混合架构：工具保证覆盖率，LLM 补充深度
  • 如何用 AST 静态分析实现代码性能反模式检测（N+1 查询、同步阻塞、字符串拼接）
  • 如何构建代码库上下文引擎，为 LLM 分析注入项目级上下文以提升审查质量
  • 如何实现内存级事件总线（发布/订阅 + 历史回放）驱动 WebSocket 实时推送
  • 如何设计负分制健康度评分模型，将多维发现量化为单一质量指标
  • 如何构建运行时指标收集器，跟踪 Review/LLM/Agent 的执行指标和审计日志

技术亮点

确定性 + LLM 双层架构

每个 Agent 都采用"确定性工具先扫描 → LLM 语义补充"的模式。Semgrep/Ruff/pip-audit/AST 确保基础检测不漏（零漏报），LLM 补充语义理解和修复建议（深度分析）。即使 LLM 不可用，系统仍能正常输出基础审查结果。

6 Agent 并行编排

ReviewService 通过 asyncio.gather() 并发执行所有 Agent，而非串行等待。每个 Agent 独立运行、独立容错，单个 Agent 失败不影响其他 Agent。结果统一聚合、去重、入库。

AST 深度分析

PerformanceAgent 使用 Python AST 模块构建自定义 Visitor，检测循环内 ORM 调用（N+1）、async 函数内同步阻塞、字符串拼接等反模式。TestCoverageAgent 通过 AST 解析测试文件引用关系，识别未测试函数。

代码库上下文引擎

ContextEngine 构建项目级索引（符号表、依赖关系、文件关联），在 LLM 分析前自动注入相关上下文，让 LLM 不仅看到当前文件，还能理解其在项目中的位置和关联，显著提升审查质量。

3. 项目定位与系统上下文

本系统是一个多 Agent 协作代码审查平台，模拟真实 Code Review 流程。用户通过 Web UI 提交项目路径和审查类型，系统触发多个专业 Agent 并行审查，由编排层汇总生成结构化审查报告和健康度评分。

4. 核心设计原则

原则含义在代码中的体现
确定性工具兜底 + LLM 语义补充 Semgrep/Ruff/pip-audit/AST 确保基础检测不漏（零漏报），LLM 补充语义理解和修复建议。LLM 失败时自动降级到纯工具结果。 每个 Agent 的 analyze() 方法都先调用确定性工具，再 try/except 调用 LLM。参见 app/agents/security_agent.py
6 Agent 并行编排 asyncio.gather 并行执行所有 Agent，结果去重聚合，最小化审查时间。单个 Agent 异常不阻塞整体。 ReviewService.run_review() 中的 asyncio.gather(*[_run_one(...)])。参见 app/services/review_service.py
可验证维度分离 每个 Agent 聚焦一个可验证的代码质量维度（安全/规范/依赖/覆盖/性能/Git），职责单一，易于扩展。 每个 Agent 继承 BaseAgent，实现独立的 analyze()。参见 app/agents/base.py
优雅降级 LLM 不可用时系统仍能正常工作（纯工具模式）；单个 Agent 失败时其他 Agent 不受影响。 所有 LLM 调用都包裹在 try/except 中，失败时 logger.warning 并返回空列表。
实时可观测 审查进度通过 WebSocket 实时推送，运行时指标（Review/LLM/Agent）全程跟踪，审计日志记录关键操作。 ProgressEmitter + MetricsTracker。参见 app/services/progress.py 和 app/services/metrics.py

5. 分层架构详解

层间依赖规则

  • 严格单向依赖：上层依赖下层，下层不依赖上层
  • Agent 层不依赖 API 层：Agent 只接收 project_path 和 file_paths，返回 list[dict]，不关心 HTTP 细节
  • 业务层通过接口编排 Agent：ReviewService 通过 Agent 注册表动态选择 Agent，不硬编码具体 Agent 类

6.1 SecurityAgent — 安全审查

代码路径app/agents/security_agent.py
确定性工具Semgrep（多规则集：python/flask/django/sqlalchemy/bandit/owasp-top-ten）
LLM 补充安全专家 Prompt，聚焦 SQL 注入、命令注入、XSS、硬编码密码、不安全反序列化

工作流程

  1. 语言检测：扫描项目文件特征（*.py、pyproject.toml、package.json 等），自动选择对应 Semgrep 规则集
  2. Semgrep 扫描：对每个规则集执行 semgrep scan --config {ruleset} --json，解析 JSON 输出，映射严重度
  3. LLM 分析：收集代码文件，通过 ContextEngine 增强 Prompt，并发调用 LLM
  4. 去重合并：按 (rule_id, file_path, line_start) 去重

严重度映射

Semgrep 原始映射后
ERRORcritical
WARNINGwarning
INFOsuggestion

6.3 DependencyAgent — 依赖审查

代码路径app/agents/dependency_agent.py
确定性工具pip-audit（Python 漏洞扫描）+ npm registry API（JS 过时检测）
LLM 补充依赖管理专家 Prompt，识别风险/弃用/过时/许可证问题

双生态扫描策略

  • Python：读取 requirements.txt → 执行 pip-audit -f json → 按 CVE 评分映射严重度（≥9.0 critical, ≥7.0 warning, ≥4.0 suggestion）
  • JavaScript：读取 package.json → 并发查询 npm registry（Semaphore 限制并发 5）→ 比对声明版本与最新版本

6.4 TestCoverageAgent — 测试覆盖审查

代码路径app/agents/test_coverage_agent.py
确定性工具Python AST 静态分析（解析函数定义 + 测试文件引用）
LLM 补充测试工程专家 Prompt，为未测试函数生成测试建议

AST 分析原理

  1. 遍历项目所有 *.py 文件，区分测试文件和源文件
  2. 对测试文件：用 ast.walk() 提取所有 ast.Name 和 ast.Attribute 引用，构建"已测试函数集合"
  3. 对源文件：用 ast.walk() 提取所有 FunctionDef / AsyncFunctionDef，跳过 _ 开头和 test_ 开头的函数
  4. 若函数名不在"已测试集合"中 → 标记为未测试
  5. 若项目完全没有测试目录 → 额外报 warning

6.5 PerformanceAgent — 性能分析审查

代码路径app/agents/performance_agent.py
确定性工具Python AST 自定义 Visitor（4 种反模式检测）
LLM 补充性能优化专家 Prompt

AST 反模式检测

反模式规则 ID检测方法严重度
N+1 查询PERF-N+1循环内 ORM 调用（query/filter/get/all 等）critical
同步阻塞PERF-SYNCasync 函数内 time.sleep/requests.get/subprocess.runcritical
字符串拼接PERF-CONCAT循环内 += 字符串拼接（O(n²)）warning
无限制查询PERF-UNBOUNDED.all() 无 .limit() 配合suggestion

AST Visitor 实现亮点

N+1 检测使用自定义 ast.NodeVisitor，通过 _loop_depth 计数器追踪循环嵌套深度。只有 _loop_depth > 0 时（即处于循环体内）才检查 ORM 调用，精准定位 N+1 反模式。

同步阻塞检测使用 ast.NodeVisitor，通过 _in_async 标志追踪是否处于 async 函数体内，再用 ast.walk() 扫描所有 ast.Call 节点，比对预定义的阻塞调用集合。

6.6 GitReviewAgent — Git 审查

代码路径app/agents/git_review_agent.py
确定性工具Git CLI（提交规范检查 + 分支策略 + 贡献统计）
LLM 补充Git 工作流专家 Prompt

4 个检测维度

  1. 提交规范：检查最近 50 条提交是否遵循 Conventional Commits（feat|fix|docs|style|refactor|perf|test|build|ci|chore|revert），统计违规比例
  2. 分支策略：检查分支命名是否符合 type/description 格式（feature/fix/hotfix/release/chore/docs），找出超 30 天未更新的陈旧分支
  3. 贡献统计：分析近 30 天提交频率（检测"突击提交"模式），统计近 90 天文件热点（高频修改文件可能存在设计问题）
  4. LLM 点评：收集仓库信息 + 提交历史 + 分支列表，LLM 综合分析

9. 实时通信架构

系统使用内存级发布/订阅事件总线（ProgressEmitter）+ WebSocket 实现审查进度的实时推送。

事件流时序

关键设计

  • 历史回放：新订阅者连接时，先回放该 review_id 的所有历史事件，避免漏掉早期进度
  • 自动清理：审查结束且所有订阅者断开后，自动清理历史事件
  • 单进程内存实现：使用 asyncio.Queue 作为订阅通道，足够本项目规模；多进程需替换为 Redis pub/sub

10. 健康度评分模型

评分模型定义在 app/services/health.py，采用负分制：从 100 分起扣，下限 0，上限 100。

扣分权重

严重度扣分/个含义
critical-15严重问题（安全漏洞、N+1 查询等）
warning-5需要关注的问题（代码规范违反、依赖漏洞等）
suggestion-2改进建议（性能优化、测试补充等）
nitpick-0.5细节优化（import 排序、分支命名等）

颜色等级

分数区间颜色含义
80-100green健康
60-79orange一般
40-59gold较差
0-39red严重
 
# app/services/health.py

SEVERITY_PENALTY = {
    "critical":   15.0,
    "warning":     5.0,
    "suggestion":  2.0,
    "nitpick":     0.5,
}

def compute_health_score(review: Review, findings: list[Finding]) -> float:
    score = 100.0
    for f in findings:
        score -= SEVERITY_PENALTY.get(f.severity, 1.0)
    return max(0.0, min(100.0, round(score, 1)))

11. LLM 集成架构

LLM 调用通过共享客户端 app/agents/llm_client.py 统一管理，所有 Agent 复用同一套调用逻辑。

调用流程

关键设计决策

  • OpenAI 兼容接口：使用标准 /chat/completions 端点，支持任意 OpenAI 兼容的 LLM 服务
  • 并发控制：Semaphore(3) 限制同时 LLM 调用数，避免 API 限流
  • JSON 容错解析：parse_json_object() 从 LLM 回复中提取 {...} 区间，容忍 markdown 代码围栏等噪音
  • Token 用量持久化：每次调用都记录到 LLMUsage 表（prompt_tokens / completion_tokens / latency_ms），重启不丢失
  • 优雅降级：LLM 不可用时，Agent 回退到纯工具结果，不阻塞审查流程

12. 上下文引擎

AgentContextEnhancer（app/agents/context_enhancer.py）在 LLM 分析前，通过 ContextEngine 构建代码库索引，为每个被审查文件补充项目级上下文。

工作原理

  1. 构建索引：ContextEngine.build(project_path) 扫描项目文件，提取符号定义、导入关系、调用链
  2. 上下文增强：enhance_prompt(file_path, base_prompt) 为指定文件查找相关文件、符号引用、调用者信息
  3. 注入 Prompt：在基础 Prompt 前注入上下文信息，让 LLM 理解文件在项目中的位置
# 注入后的 Prompt 结构：
#
# 以下是代码库上下文（帮助理解被审查文件在整个项目中的位置）：
#
# [相关文件、符号引用、调用者信息等]
#
# ---
#
# [原始 Agent Prompt]
# 你是一个代码安全专家。请分析以下代码...

降级策略：若 ContextEngine 构建失败（如项目过大、解析错误），自动降级为无上下文模式，直接使用原始 Prompt。

14. 技术选型与决策

后端框架：FastAPI vs Django vs Flask

维度FastAPI ✅DjangoFlask
异步支持原生 async/await有限（ASGI 适配）需扩展
自动文档内置 OpenAPI/Swagger需第三方需第三方
数据验证Pydantic 内置Serializer需扩展
WebSocket原生支持需 Channels需扩展
性能高（Starlette）中中

选择理由：本项目核心是异步并行 Agent 编排 + WebSocket 实时推送，FastAPI 的原生 async 和 WebSocket 支持是决定性优势。

ORM：SQLAlchemy 2.0 vs Tortoise ORM

维度SQLAlchemy 2.0 ✅Tortoise ORM
类型注解Mapped 类型注解，IDE 友好类似 Django Model
异步支持AsyncSession 原生支持原生异步
生态成熟度Python ORM 事实标准较新
灵活性极高（支持复杂查询）中等

静态分析工具选型

工具用途选择理由

16. 术语表

术语英文说明
FindingFindingAgent 发现的一个代码问题，包含严重度、文件位置、代码片段、修复建议
健康度评分Health Score基于 Finding 的负分制质量分数（0-100），反映项目代码质量
AgentAgent负责特定维度代码分析的独立模块，每个 Agent 可包含确定性工具和 LLM 两层
确定性工具Deterministic ToolSemgrep/Ruff/pip-audit/AST 等传统静态分析工具，结果可复现，零漏报
上下文引擎Context Engine构建代码库索引，为 LLM 分析注入项目级上下文（相关文件、符号引用等）
事件总线Progress Emitter内存级发布/订阅系统，驱动 WebSocket 实时推送审查进度
Agent 注册表Agent RegistryReviewService 中的字典映射，根据审查类型动态选择 Agent 组合
负分制Negative Scoring从 100 分起扣的评分模型，每个 Finding 按严重度扣分
Conventional CommitsConventional Commits提交消息规范格式：type(scope): description
N+1 查询N+1 Query循环内逐条查询数据库的性能反模式，应改为批量查询
